# Exposing a gateway without losing your endpoints

keysmith can publish itself through Cloudflare's `cloudflared` — no ports opened, no
router config, no TLS certificate to babysit. There are two ways to do it and the
difference between them is the whole reason this file exists.

## Quick tunnel: fine for a trial, wrong for a client you keep

```bash
keysmith serve --tunnel            # no named tunnel configured → quick mode
```

This is `cloudflared tunnel --url http://127.0.0.1:8787`. It is free, needs no account
and no login, and hands you a hostname like
`https://random-words-3.trycloudflare.com/v1`.

That hostname is allocated when the process starts and **revoked when it stops**. Every
client you pointed at it — a desktop app, a phone, a colleague's script — goes silently
dead on the next restart, and "silently" is the problem: a custom-endpoint entry in most
clients does not error, it just stops answering, so you get to rediscover which twelve
config files reference a URL that no longer resolves. If you are here for a demo that
lasts one evening, quick mode is exactly right, and keysmith prints a warning telling you
it is quick mode.

## Named tunnel: the one you paste into a client and forget

Requirements: `cloudflared` installed, and a Cloudflare account with **your own domain**
on it (the free plan is enough — this uses DNS records, not paid features).

```bash
brew install cloudflared
cloudflared tunnel login                     # opens a browser, writes ~/.cloudflared/cert.pem
keysmith tunnel status                       # what keysmith can see right now

keysmith tunnel setup llm.example.com        # prints exactly what it will run
keysmith tunnel setup llm.example.com --yes  # does it
```

`setup` runs, in order:

1. `cloudflared tunnel create keysmith` (idempotent — an existing tunnel of that name is
   reused, and its UUID is what the config references);
2. `cloudflared tunnel route dns keysmith llm.example.com` — one AAAA record in your DNS;
3. writes `~/.cloudflared/keysmith.yml`:

```yaml
# generated by `keysmith tunnel setup` — keysmith rewrites this file, edit with that in mind
tunnel: 0f2f4a4e-…
credentials-file: ~/.cloudflared/0f2f4a4e-….json

ingress:
  - hostname: llm.example.com
    service: http://127.0.0.1:8787
  - service: http_status:404
```

and records `{name, hostname, configFile}` in `config.json.tunnel`. From then on
`keysmith serve --tunnel` and `keysmith start --tunnel` use `tunnel run` with that file,
and the URL is `https://llm.example.com/v1` for as long as you keep the record.

That trailing `http_status:404` rule is deliberate: any hostname you have not mapped in
the ingress gets a 404 from Cloudflare's edge instead of reaching your machine.

## What the tunnel does *not* do

It is transport, not authentication. Everything under `/v1`, and the status page, still
require the key — so a stray crawl of `https://llm.example.com/` costs an attacker
nothing but a 401. Keep:

- `host: "127.0.0.1"` (the default). The tunnel connects to localhost; binding `0.0.0.0`
  additionally exposes the gateway to your whole LAN and makes the tunnel pointless.
- `auth.enabled: true`. Turning it off is only sane behind a loopback you trust.
- `limits.maxConcurrent`, and per-adapter `maxConcurrent`/`timeoutMs`. A CLI adapter is a
  process spawner; without a cap, one busy page on the open internet is a
  denial-of-wallet machine — it burns your agent quota and then your file descriptors.

Cloudflare does not see the body of your requests except as an HTTPS tunnel endpoint it
is carrying for you; the traffic still terminates on your machine and is forwarded to the
upstreams you configured. Do not put a gateway holding other people's API keys on a
hostname you did not choose.

## Operations

```bash
keysmith tunnel status            # installed? logged in? named? on-disk ingress?
keysmith tunnel run               # just the tunnel, against a gateway already running
keysmith status                   # process, config, adapters, tunnel, /healthz
tail -f ~/.local/share/keysmith/keysmith.log
```

`--tunnel` on `serve`/`start` inherits the named tunnel from config. If the tunnel dies
(a laptop sleeping through a Cloudflare reconnect is the common case), `cloudflared`
reconnects itself; if it exits, restart with `keysmith start --tunnel`. To move to a new
hostname, re-run `keysmith tunnel setup <new host> --yes` — it routes DNS and rewrites the
ingress file.

If your client needs the URL to survive the machine being off: it will not. A tunnel is
not a queue. Anything that must not lose requests should point at a gateway that is
actually always on.
